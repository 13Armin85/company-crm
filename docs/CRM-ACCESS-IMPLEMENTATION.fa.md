# گزارش اجرای مأموریت کامل دسترسی Company CRM

## ۱. خلاصه پیاده‌سازی

تغییرات روی شاخهٔ `crm/access-redesign-complete` در کد واقعی Django، React و PostgreSQL پیاده‌سازی شدند. موتور مرکزی دسترسی، کاتالوگ ۵۲ مجوز در ۱۱ گروه، نقش‌های چندگانه، استثناهای زمان‌دار Allow/Deny، جانشینی اولویت‌دار، عدم حضور، مدیریت مستقل هویت/رمز/حذف عضویت و محافظت ورود/خروج تکمیل شدند. پنل‌ها به API واقعی متصل‌اند.

Level/LevelId دیگر به عنوان مکانیزم Authorization سیستم CRM استفاده نمی‌شود.

Admin عادی قادر به ساخت Permission فنی جدید نیست.

Backend Authorization مستقل از مخفی یا نمایش داده شدن UI در React اعمال می‌شود.

## ۲. تغییرات Backend

- رجیستری مجوزها در کد توسعه‌دهنده و فرمان تکرارپذیر `sync_crm_permissions`؛ کاتالوگ فقط خواندنی از API، پشتیبانی از کد نقطه‌دار و غیرفعال‌ماندن مجوز ناشناخته.
- ترکیب مجوز نقش‌های فعال و محاسبهٔ `DENY > ALLOW > Role > Delegation > No Access` با محدودهٔ Workspace و عضویت/حساب فعال. Cache فقط درون درخواست است؛ درخواست بعدی محرومیت یا انقضا را فوراً می‌بیند.
- مجوز مستقل عملیات و فیلدهای حساس، کنترل محدودهٔ پروژه، محافظ مسیرهای قدیمی اعضا/دعوت/پروژه/Issue و API کلیدمحور؛ نقش عددی Plane نقش Adapter دارد.
- اعتبارسنجی بازه، روابط همان شرکت و تکرار استثنا؛ محدودیت دیتابیس برای اثر معتبر و تکرار دقیق فعال. تعارض Allow/Deny نتیجهٔ قطعی و توضیح قابل نمایش دارد.
- جانشین فعال، حاضر و عضو شرکت با کمترین اولویت انتخاب می‌شود. فقط مجوزهای نقش مدیر با قابلیت واگذاری منتقل می‌شوند؛ استثنا یا جانشینی زنجیره‌ای منتقل نمی‌شود. پایان عدم حضور مجوز موقت را باطل می‌کند.
- کنترل رابطهٔ مدیر بالادستی برای ثبت/ویرایش/پایان غیبت؛ مجوز سراسری مستقل برای مدیر مجاز شرکت. ترتیب جانشین تکراری یا کاربر نامعتبر رد می‌شود.
- تغییر رمز مستقل با تأیید، سیاست Django و Hash استاندارد؛ نشست‌های قبلی همان حساب در درخواست بعدی نامعتبر می‌شوند. رمز و توکن در Audit و لاگ درخواست redact می‌شوند.
- حذف، عضویت همان شرکت را باطل می‌کند و هویت سراسری، عضویت شرکت دیگر و تاریخچه را نگه می‌دارد. آخرین مدیر مؤثر قابل حذف، غیرفعال‌سازی یا محروم‌سازی فعلی/زمان‌بندی‌شده نیست.
- ثبت‌نام عمومی رمز/Magic/OAuth حتی با تنظیم قدیمی آزاد نمی‌شود. دعوت معتبر و اثبات مالکیت ایمیل/توکن برای ایجاد حساب لازم است؛ عضویت خودکار در نخستین شرکت حذف شده است.
- API خصوصی بدون نشست معتبر 401 می‌دهد؛ درخواست تغییردهندهٔ دارای کوکی به CSRF معتبر نیاز دارد و پاسخ‌های مدیریت `private, no-store` دارند.

شرح معماری و جانشینی در [سند معماری](CRM-ACCESS-REDESIGN.fa.md)، کدها در [کاتالوگ مجوزها](CRM-PERMISSION-CATALOG.md) و ورودی/خروجی/خطاها در [قرارداد API](CRM-ACCESS-API.fa.md) آمده‌اند.

## ۳. تغییرات Frontend

- منوی کاربر برای مدیر مجاز دقیقاً سه عملیات دارد: «تغییر اطلاعات هویتی»، «تغییر رمز عبور» و «حذف کاربر». هر عملیات مجوز خودش را دارد. تغییر مستقیم نقش در جدول حذف شده است.
- پروفایل مدیریتی نام، ایمیل، نام کاربری، نقش‌های سازمانی متعدد، واحدها و وضعیت عضویت را ویرایش می‌کند؛ رمز در فرم هویت وجود ندارد.
- Modal رمز با نام کاربر، دو فیلد الزامی، نمایش/مخفی‌سازی، تطابق، حالت ارسال، انصراف، خطای Backend و پیام موفقیت به API مستقل متصل است.
- نقش‌ها دارای جستجو، توضیح، شمار مجوز/کاربر، وضعیت فعال و مشاهده/ویرایش مجوزها هستند. Permission Catalog جستجو و دسته‌بندی دارد و قابل ساخت توسط ادمین نیست.
- پروفایل، افزودن/ویرایش/حذف استثنا و منبع دسترسی مؤثر/تعارض را نمایش می‌دهد. پنل واحد ترتیب جانشینان و صفحهٔ عدم حضور، وضعیت و جانشینی فعال را مدیریت می‌کنند.
- `usePermission`، `useAnyPermission`، `PermissionGate` و نقشهٔ مسیرها از پاسخ Backend استفاده می‌کنند. پس از خطای دریافت دسترسی، مجوز کش‌شده قابل استفاده نیست و cache شرکت‌ها مستقل است.
- Login بیرون از Shell خصوصی است؛ قبل از تأیید نشست، Shell و query خصوصی mount نمی‌شوند. خروج، cache و state خصوصی را پاک و درخواست‌ها را لغو می‌کند؛ رویداد بین تب‌ها فقط nonce تصادفی دارد.
- بررسی دوبارهٔ نشست هنگام مسیر/focus/بازگشت مرورگر، مخفی‌شدن هم‌زمان Shell و portalهای Modal هنگام pagehide و جلوگیری از احیای نشست توسط پاسخ دیررس اعمال شده‌اند.
- Selector مشترک در `@plane/ui` دارای گروه، جستجو، شمارنده، chip انتخاب‌شده، حذف انتخاب و آواتار کاربر است و Storybook دارد. PasswordInput مشترک برچسب فارسی و وضعیت قابل دسترس دارد.
- فونت Vazirmatn از فایل محلی بستهٔ مشترک بارگذاری می‌شود؛ مسیر asset برای web/admin/space اصلاح شده است. فرم‌ها و Modalها برای RTL، موبایل و دو پوسته تنظیم شده‌اند.

## ۴. Database

سه migration جدید: `0128_crm_access_control` برای مدل/فیلد/قید، `0129_crm_access_data` برای آرشیو/انتقال و جایگزینی Level و `0130_crm_exception_constraints` برای اثر و یکتایی استثنا.

0129 کاربران، عضویت‌ها، نقش‌های سفارشی و روابط مسیریابی را حفظ می‌کند؛ مقادیر قدیمی Level و وضعیت مجوزها آرشیو می‌شوند. چهار کد قدیمی تیکت به مجوزهای متناظر جدید نگاشت می‌شوند و ارتباط‌های اولیه حفظ می‌شوند. حذف ستون‌ها پس از جایگزینی مصرف‌کنندگان runtime انجام می‌شود. 0130 نسخه‌های دقیقاً تکراری استثنا را حذف نمی‌کند؛ با آرشیو، فقط نسخه‌های اضافه را غیرفعال می‌کند.

انتقال روی دیتابیس مجزای دارای داده، اجرای تکراری و rollback تا 0128 تست شده‌اند. اجرای عملیاتی انجام نشده است. دستورها، نگاشت کدهای قدیمی و محدودیت بازگشت در [راهنمای انتقال](CRM-ACCESS-MIGRATION.fa.md) آمده‌اند.

بررسی واقعی Chrome با build تولید و API متصل به دیتابیس مجزای `test_plane` انجام شد. نتایج سناریوهای عملی و تصاویر در خروجی مرورگر ثبت شدند:

۱۳ بررسی نهایی موفق بودند و خطای Runtime مشاهده نشد. دکمه‌های متنی عملیات در موبایل نیز از نظر جاگیری متن و عدم تقاطع اندازه‌گیری شدند و موفق بودند.

- ورود مستقیم ناشناس به مسیر خصوصی، بدون Shell و query خصوصی، به Login منتقل شد.
- منوی سه عملیات، نمایش/مخفی‌سازی رمز، رد تأیید ناهماهنگ و ذخیرهٔ واقعی رمز بررسی شدند.
- ساخت/جستجوی نقش، انتخاب و chip مجوز، ویرایش استثنا و توضیح تعارض Allow/Deny با API واقعی کار کردند؛ پروفایل فیلد رمز نداشت.
- ترتیب جانشین ذخیره شد، عدم حضور فعال ایجاد شد، منبع `delegation` برای عضو مشاهده شد و پس از پایان غیبت، دسترسی موقت همان عضو فوراً رد شد.
- خروج هر دو تب را پاک کرد؛ Back، Refresh و URL خصوصی به Login برگشتند و API خصوصی پس از خروج 401 داد.
- handler بازگشت صفحه با رویدادهای `pagehide/pageshow` و `persisted=true` در مرورگر بررسی شد: مخفی‌شدن هم‌زمان، تأیید مجدد نشست معتبر و انتقال به Login پس از حذف کوکی همگی موفق بودند. استفادهٔ واقعی Chrome از snapshotِ bfcache در پیمایش Native جداگانه اندازه‌گیری نشده است.
- تصاویر Login، نقش و عدم حضور در عرض ۳۹۰ و تصاویر رمز، سازمان و تیم تیره در عرض ۱۴۴۰ بررسی شدند. RTL، بارگذاری واقعی فایل Vazirmatn و نبود overflow افقی صفحه تأیید شدند. جدول‌های عریض داخل ظرف خود اسکرول می‌شوند.

خروجی محلی مرورگر در `tmp/crm-v2-browser/results.json` و شش تصویر همان پوشه است. حساب‌ها و داده‌ها فقط fixture تست بودند؛ رمز راه‌اندازی تصادفی در محیط موقت نگه داشته شد. API و Chrome آزمایشی پس از اجرا متوقف شدند.

## ۷. نکات Deployment

انتشار Backend و Frontend باید هماهنگ باشد. ابتدا backup قابل بازیابی از PostgreSQL و اجرای آزمایشی روی کپی داده؛ سپس با روال مقصد `manage.py migrate` و `manage.py sync_crm_permissions` اجرا شوند. سرویس جدید یا تغییر اجباری Docker/Environment نیاز نیست. انقضای مجوز موقت در هر درخواست محاسبه می‌شود و به کار دوره‌ای Celery وابسته نیست.

مصرف‌کنندگان قدیمی Level باید پیش از حذف ستون‌ها متوقف شوند. راهنمای rollback تا 0128 موجود است؛ بازگشت به پیش از 0128 پس از ایجاد دادهٔ جدید مناسب نیست. هیچ دیتابیس یا Volume عملیاتی دست‌کاری نشده و هیچ commit، push یا merge انجام نشده است.

## ۸. محدودیت‌ها

- بازطراحی کامل گردش ارجاع مطابق مأموریت به مرحلهٔ بعد موکول شده است؛ گردش موجود حفظ و مجوزهای آینده در کاتالوگ آماده‌اند.
- کل مجموعهٔ چندماژولی Backend اجرا نشده است؛ تست‌های مرتبط با تغییرات موفق بودند. تأیید دادهٔ واقعی مقصد پیش از انتشار همچنان باید روی کپی همان داده انجام شود.
- مرورگر واقعی بررسی‌شده Chrome در دو اندازه است؛ همهٔ مرورگرها و اندازه‌ها پوشش داده نشده‌اند. Back واقعی بررسی شد، ولی استفادهٔ قطعی مرورگر از bfcache در آن اجرا اندازه‌گیری نشده است.
- `pnpm check` به علت خطاهای قالب‌بندی منابع دست‌نخوردهٔ پروژه موفق نیست؛ lint/types/build مستقل و قالب‌بندی فایل‌های این تغییر جداگانه بررسی می‌شوند. هشدارهای موجود ابزارها و اندازهٔ chunk باقی‌اند.
- UI دسترسی را هر ۳۰ ثانیه و هنگام focus تازه می‌کند؛ Backend هر درخواست را مستقلاً کنترل می‌کند.
- نگاشت کدهای قدیمیِ امکانات آینده مانند مالی/فروش تعیین نشده است؛ رکوردها حفظ و غیرفعال‌اند و هنگام توسعهٔ همان امکانات باید نگاشت شوند.
- Adapter عددی و guardهای داخلی Plane در ماژول‌های خارج از محدودهٔ CRM حفظ شده‌اند؛ عملیات CRM تغییرکرده از موتور مرکزی استفاده می‌کنند.
- استقرار روی سرور و migration دیتابیس عملیاتی انجام نشده است.
