# راهنمای انتقال امن سیستم دسترسی CRM

این راهنما برای انتشار تغییرات است. دیتابیس و Volume سرور عملیاتی تغییر نکرده‌اند. اجرای Docker محلی و بررسی حفظ داده‌های آن در [راهنمای Docker محلی](CRM-DOCKER-LOCAL.fa.md) توضیح داده شده است. دستورات باید با سرویس API و تنظیمات همان محیط مقصد اجرا شوند.

## پیش از انتشار

۱. از PostgreSQL نسخهٔ پشتیبان سازگار تهیه و بازیابی آن را روی دیتابیس مجزا بررسی کنید. شناسه‌های کاربران، عضویت‌ها، نقش‌ها، روابط واحد و رکوردهای مسیریابی را در بررسی بازیابی حفظ کنید.

۲. کد جدید و migrationها را روی یک کپی دارای داده اجرا کنید. دسترسی مدیر اصلی، اعضای عادی، نقش‌های سفارشی و ارتباطات مسیریابی را با دادهٔ مقصد بررسی کنید. همگام‌سازی دوباره نباید تخصیص عمدی نقش‌ها را بازنویسی کند.

۳. نسخهٔ قبلی کد و backup مربوط به همان نسخه را برای بازگشت نگه دارید. انتشار Backend، Frontend و اجرای migration باید هماهنگ باشد؛ مصرف‌کنندهٔ قدیمی فیلد Level نباید هنگام حذف ستون‌ها فعال بماند.

## ترتیب migrationها

| Migration                        | اثر                                                                                                        |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `0128_crm_access_control`        | ساخت استثنا، جانشینی و عدم حضور؛ تکمیل کاتالوگ و نقش‌های سیستمی                                            |
| `0129_crm_access_data`           | آرشیو مقدارهای Level و required_level؛ نگاشت کاربران؛ حذف ستون‌ها پس از جایگزینی تمام مصرف‌کنندگان runtime |
| `0130_crm_exception_constraints` | جلوگیری از اثر و تکرار نامعتبر؛ کنارگذاری فقط استثناهای دقیقاً تکراری همراه آرشیو برگشت                    |

0129 نقش‌های سفارشی، کاربران، عضویت‌ها، واحدها، تصمیم‌های ارجاع، قوانین و صف‌های موجود را حفظ می‌کند. نقش عددی ۲۰ Plane به نقش سازمانی پایهٔ مدیر و دیگر عضویت‌ها به عضو نگاشت می‌شوند؛ تخصیص‌های قبلی نقش‌های سفارشی باقی می‌مانند. رتبهٔ عددی هیچ نقشی در Authorization جدید ندارد. قوانین مسیریابی از ارتباط نقش موجود و مدیر حاضر/جانشین معتبر استفاده می‌کنند.

حذف ستون‌های قدیمی در 0129 پس از انتقال مقدارهای آن‌ها به آرشیو قابل بازگشت انجام می‌شود. آرشیو از پاک‌سازی دوره‌ای لاگ مستثناست. بازطراحی گردش ارجاع در این انتشار انجام نشده است.

0129 پیش از حذف ستون‌ها، قیدهای معوق PostgreSQL را با `SET CONSTRAINTS ALL IMMEDIATE` بررسی می‌کند. ساخت نقش‌ها و روابط و تغییر ساختار همچنان در یک تراکنش انجام می‌شود؛ این ترتیب از خطای `pending trigger events` هنگام نخستین اجرا روی دیتابیس دارای داده جلوگیری می‌کند.

مجوزهای فعال قدیمی تیکت و روابط نقش‌های آن‌ها طبق جدول زیر منتقل می‌شوند. شناسه و رابطهٔ قدیمی حذف نمی‌شود؛ رابطهٔ متناظر به مجوز جدید اضافه می‌شود.

| کد قدیمی         | کد جدید                          |
| ---------------- | -------------------------------- |
| `ticket-view`    | `Issue.View`                     |
| `ticket-assign`  | `Issue.Assign` و `Routing.Route` |
| `ticket-resolve` | `Issue.Status.Edit`              |
| `ticket-approve` | `Referral.Approve`               |

وضعیت اولیهٔ مجوزهای قبلی و شناسهٔ رابطه‌های جدیدِ ساخته‌شده در migration آرشیو می‌شوند. Rollback وضعیت اولیه را بازمی‌گرداند و فقط رابطه‌های ساخته‌شده توسط همین انتقال را کنار می‌گذارد. مجوزهای قدیمیِ غیرفعال یا حذف‌شده دسترسی جدید ایجاد نمی‌کنند. کدهای ناشناخته یا متعلق به امکانات آینده مانند فروش/مالی حفظ و غیرفعال می‌شوند؛ نگاشت خودکار آن‌ها به مجوز گسترده انجام نمی‌شود و باید هنگام توسعهٔ همان ماژول تعیین شود.

0130 رکوردهای تکراری با کاربر، Workspace، مجوز، اثر و مرزهای زمانی یکسان را حذف نمی‌کند. فقط نسخه‌های اضافه را غیرفعال می‌کند؛ یک رکورد فعال با همان اثر و بازه باقی می‌ماند و نتیجهٔ دسترسی تغییر نمی‌کند. وضعیت قبلی در آرشیو `crm-migration:0130:Exception:` نگه داشته می‌شود. استثناهای Allow و Deny متفاوت با هم ادغام نمی‌شوند.

## اجرا و بررسی

```sh
python manage.py check
python manage.py migrate --plan
python manage.py migrate
python manage.py sync_crm_permissions
python manage.py makemigrations --check --dry-run
```

برای بررسی یک شرکت، فرمان `sync_crm_permissions --workspace <slug>` قابل استفاده است. فرمان idempotent است، مجوز ناشناخته را غیرفعال نگه می‌دارد و مجوزهای عمدی نقش‌های موجود را دوباره تخصیص نمی‌دهد.

بعد از انتشار، ورود با کاربر مدیر، `access/me/`، ساخت/ویرایش کاربر، استثنای Deny، جانشینی و دسترسی پس از خروج را بررسی کنید. امکان تغییر نقش یا کاتالوگ با حساب بدون مجوز باید رد شود. رابط جدید و پاسخ Backend باید هم‌زمان از کدهای مجوز استفاده کنند.

برای این قابلیت سرویس جدید، dependency جدید یا تغییر اجباری Docker لازم نیست. صحت انقضای جانشینی و استثنا وابسته به Celery Beat نیست. ثبت‌نام عمومی حتی با مقدار قدیمی `ENABLE_SIGNUP=1` آزاد نمی‌شود؛ ایجاد حساب مدیریتی و دعوت سازمانیِ باز یا پذیرفته‌شده همچنان مجازند. ساخت حساب با رمز از مسیر دعوت به `invitation_token` همان دعوت نیاز دارد؛ Magic/OAuth کنترل ایمیل را اعتبارسنجی می‌کنند. دعوت ردشده یا حذف‌شده مجاز نیست. ورود یا ساخت حساب به‌صورت خودکار کاربر را عضو نخستین شرکت نمی‌کند.

## برنامهٔ بازگشت

در دیتابیس مجزا، بازگشت به `0128_crm_access_control` بررسی شده است. 0129 ستون‌های قدیمی را بازمی‌گرداند و مقدارهای قبلی را از آرشیو بازیابی می‌کند؛ 0130 وضعیت رکوردهای دقیقاً تکراری را بازیابی می‌کند. جدول‌های استثنا، غیبت و جانشینی در 0128 همچنان وجود دارند.

بازگشت نرم‌افزار باید همراه نسخهٔ متناظر کد و بررسی داده‌های ایجادشده پس از انتشار انجام شود. پیش از rollback عملیاتی نیز backup جدید تهیه شود. بازگشت به پیش از 0128 جدول‌های جدید را از بین می‌برد و برای محیط دارای دادهٔ جدید مناسب نیست. ریست دیتابیس، حذف Volume یا حذف دستی داده جزو این روال نیست.

تست واقعی `test_crm_access_migration.py` دادهٔ قدیمی دارای نقش سفارشی را مهاجرت می‌دهد، انتقال را دوباره اجرا می‌کند، حفظ شناسه‌ها و روابط را بررسی می‌کند، مقدار Level را پس از rollback بازیابی می‌کند و حفظ/بازگشت استثناهای تکراری 0130 را نیز می‌سنجد.

این تست حفظ مجوز `ticket-view` و رابطهٔ اصلی آن، ایجاد دسترسی متناظر `Issue.View`، غیرفعال‌شدن کد قدیمی و بازیابی دقیق آن در rollback را نیز بررسی می‌کند.

اجرای نخست 0129 در همین تست بدون پیش‌اجرای تابع انتقال انجام می‌شود تا خطاهای قیدهای معوق در تراکنش واقعی نیز پوشش داده شوند.
