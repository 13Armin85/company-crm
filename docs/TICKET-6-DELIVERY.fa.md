# تکمیل موتور فرم و جدول — تیکت ۶

این تحویل مربوط به تیکت ۶ است. شروع تیکت ۷ طبق متن مأموریت، به تأیید این مرحله وابسته است.

## استفاده

- مدخل مستقل «جدول‌ها و رکوردها» از ناوبری حذف شده است. کارهای پروژه و کارهای مستقل در دو نمای «کارها» و «کارهای من» از یک مدل و یک فرم طراحی استفاده می‌کنند. مسیرهای عمیق رکورد و API قدیمی برای سازگاری باقی‌اند. «جدول من» تنظیم ستون‌ها، ترتیب، عرض، پین، فیلتر، مرتب‌سازی، گروه‌بندی و ستون‌های خلاصه را در سرور ذخیره می‌کند.
- در «طراحی فرم‌ها و جدول‌ها» (`/settings/engine`) موجودیت را از فهرست قابل جستجو انتخاب کنید. «ورودی‌های فرم»، «چیدمان فرم»، «پیش‌نمایش»، «نسخه‌ها»، «جدول و تب‌ها»، «قواعد ثبت» و «ارتباط‌ها» جدا هستند. ویرایش تعریف ورودی در پنل جدا باز می‌شود. تب ورودی‌ها فقط فیلدهای همان فرم را نشان می‌دهد؛ کتابخانهٔ مشترک در چیدمان قابل جستجو است. فیلدهای هسته‌ای قفل‌اند و فرم ایجاد و ویرایش چیدمان مشترک دارند.
- روی فضای عادی ردیف کلیک کنید تا خلاصه باز شود. ویرایش، انصراف، رکورد قبلی/بعدی، صفحه کامل و رکوردهای مرتبط در این پنل در دسترس‌اند. لینک و تیک انتخاب ردیف پنل را باز نمی‌کنند.
- «ورود Excel» الگو و گزارش هر ردیف را ارائه می‌دهد. ردیف تکراری مسدود می‌شود؛ مقدار فیلد مخفی و شماره خودکار نادیده گرفته می‌شود و هشدار ثبت می‌شود.

## تصمیم‌های پیاده‌سازی

قالب شماره با تصمیم کارفرما `TT1921` و با طول شش رقم `TT001921` است. شماره جدید از شمارنده قفل‌شده و تخصیص پایدار با محدودیت یکتای دیتابیس گرفته می‌شود؛ حذف رکورد شماره را آزاد نمی‌کند. شماره‌دهی سوابق پیش‌نمایش و تأیید امضاشده با محدودیت زمانی دارد. پیشوند زیرنوع و توالی مشترک یا مستقل قابل تنظیم است.

رابطه‌ها در جدول پیوند با ایندکس ذخیره می‌شوند و نمایش دوطرفه آن‌ها در داده رکورد، در همان تراکنش به‌روز می‌شود. ستون‌های ارتباطی، Lookup، فیلتر، مرتب‌سازی، خروجی و گزارش‌های بعدی همگی از `EntityQuery` می‌خوانند. مسیر رابطه حداکثر سه سطح دارد. داده مقصد با دسترسی موجودیت، دامنه رکورد و فیلد مقصد فیلتر می‌شود.

یکتایی از یک تابع نرمال‌سازی و اعتبارسنجی مشترک در ثبت، ویرایش، ویرایش سلول، عملیات گروهی و ورود Excel استفاده می‌کند. APIهای اصلی موجودیت‌های بومی نیز از همین سیاست عبور می‌کنند. ایندکس عبارت نرمال‌شده برای موجودیت سفارشی ساخته می‌شود. ایندکس یکتا برای تمام قواعد مناسب نیست، زیرا حالت هشدار و حفظ تکرارهای قدیمی باید پشتیبانی شوند؛ جلوگیری از رقابت با قفل تراکنشی تضمین می‌شود.

وضعیت «مخفی از فرم» از نمایش جدول و مجوز مشاهده جداست. داده قبلی باقی می‌ماند و نوشتن از API نیز ممنوع است. حذف فیلد دارای داده ممنوع است؛ حذف فیلد خالی آن را از نسخه فعلی فرم جدا می‌کند و نسخه‌های تاریخی را تغییر نمی‌دهد.

جدول‌های شخصی و پیش‌فرض کاربر در دیتابیس هستند. ستون نامجاز حذف می‌شود. اگر دسترسی فیلتر ذخیره‌شده لغو شود، نتیجه خالی با پیام اصلاح فیلتر نشان داده می‌شود تا دامنه داده ناخواسته باز نشود. فیلتر نامجاز مستقیم از API همچنان رد می‌شود.

کاربر و واحد سازمانی به مدل‌های واقعی سازمان متصل‌اند. عملیات ساخت و ویرایش آن‌ها سیاست‌های موجود تخصیص نقش، واحد و حساب را استفاده می‌کند. رمز عبور در جدول، داده رکورد و لاگ موتور بازگردانده نمی‌شود.

مدل رسمی همهٔ کارها `Issue` با پروژهٔ اختیاری است. مهاجرت‌های `0144` تا `0148` کارهای مستقل قدیمی را با همان شناسه، مسئول، وضعیت، اولویت، تاریخ، شماره و زمان ساخت به جدول `issues` منتقل می‌کنند. `WorkspaceTask` فقط proxy سازگاری API قدیمی است. جدول قبلی به `workspace_tasks_archive_20261026` تغییر نام داده و برای بازیابی نگه داشته شده است. کلیدهای خارجی آرشیو برای جلوگیری از انسداد عملیات جاری جدا شده‌اند. نسخه‌های تاریخی فرم، تنظیمات جدول، روابط و رویدادهای قدیمی به موجودیت واحد «کار» مرتبط شده‌اند. ابتدا مهاجرت روی کپی مستقل پایگاه داده و سپس روی نسخهٔ محلی انجام شد؛ بکاپ پیش از مهاجرت `tmp/ticket-6-evidence/before-work-unification.dump` است.

## آزمون و شواهد

گزارش اجرای پیوستهٔ هر ۳۳ سناریوی تیکت ۶ در `tmp/ticket-6-evidence/acceptance/report.json` است؛ همهٔ آن‌ها `passed` دارند. تصاویر `scenario-01.png` تا `scenario-33.png` و نمای مرور `index.html` در همان پوشه‌اند. داده‌های نمونه با پیشوند `t6a-` از داده کاری جدا هستند؛ ساخت داده از API احرازشده و بررسی رابط با Chrome واقعی انجام شده است. نشست دوم، context مستقل مرورگر است. گذرواژه‌های آزمون در گزارش ذخیره نمی‌شوند و عضویت حساب‌های موقت پس از اجرا برداشته می‌شود.

اجرای مجدد:

```powershell
node apps/web/tests/browser/crm-ticket-six-acceptance.mjs
```

آزمون‌های قرارداد تیکت ۶، طراحی صفحه و مدل مشترک کار در مجموع ۷۸ مورد موفق شدند؛ ۳۳ آزمون رابط نیز موفق‌اند. آزمون کارایی ۱۰ هزار رکورد و ۱۰۰ شرکت در `tmp/ticket-6-evidence/performance.json` ثبت شده است. اجرای بک‌اند از stack جداگانه `docker-compose-test.yml` استفاده می‌کند. یک آزمون قدیمی خارج از تیکت ۶ در `test_workspace_tasks.py` انتظار دارد عضو عادی بتواند کار پروژه را به فرد بیرون از عضویت همان پروژه ارجاع دهد و او خودکار عضو پروژه شود؛ سیاست فعلی `validate_project_transfer` آن را با ۴۰۰ رد می‌کند. این تعارض آزمون و سیاست موجود ثبت شده و قانون ارجاع بدون تصمیم کارفرما تغییر نکرده است.

## Docker

نسخه محلی از تنظیمات موجود پروژه و volumeهای فعلی استفاده می‌کند:

```powershell
docker compose -p company-crm-local --env-file .env.dev -f docker-compose-dev.yml -f docker-compose-workstation.yml build api frontend
docker compose -p company-crm-local --env-file .env.dev -f docker-compose-dev.yml -f docker-compose-workstation.yml up -d --no-build --wait --wait-timeout 900 api worker beat-worker frontend
docker exec company-crm-local-api-1 python manage.py migrate --noinput
docker exec company-crm-local-api-1 python manage.py sync_entity_engine
```

نشانی رابط: `http://localhost:3000`. تصویرهای `company-crm-local-api:latest` و `company-crm-local-frontend:latest` بازسازی شدند و API، worker، beat و frontend در Docker سالم‌اند. ۳۳ سناریوی مرورگر پس از همین بازسازی یک‌بار دیگر موفق شدند. این stack همان محیط توسعه محلی پروژه است. از پایگاه داده پیش از مهاجرت در `tmp/ticket-6-evidence/before-work-unification.dump` پشتیبان گرفته شده است. volumeها بازنشانی نمی‌شوند. شروع تیکت ۷ طبق پیش‌نیاز درخواست منتظر تأیید این مرحله است.
